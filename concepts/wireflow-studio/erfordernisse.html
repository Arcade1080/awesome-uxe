Erfordernisse machen die Story Map zum Nutzungskontext

Unter jedem Schritt steht, was Menschen erkennen, wissen oder entscheiden können müssen, und woher wir das wissen. Das System kommt erst eine Ebene tiefer vor, bei den Nutzungsanforderungen. Screens sind dort nur noch eine Antwort auf eine belegte Frage.

Aktivität→Schritt→Erfordernis→Nutzungsanforderung→Screengrün: ohne Lösung · blau: mit System

Schablone beim Schreiben

So würde der Editor in der Map ein Erfordernis anlegen. Der Satz und die Prüfungen ändern sich beim Tippen mit.

    Prüfungen, die Claude und der Canvas machen

    Patient:innen müssen im Dropdown ihre Kasse wählen können.
    Lösung auf der falschen Ebene
    Patient:innen müssen angeben können, wie sie versichert sind, damit nur passende Praxen übrig bleiben.
    Patient:innen müssen freie Termine sehen und buchen können.
    Zwei Verben, also zwei Erfordernisse
    … freie Termine erkennen können, um … / … einen Termin verbindlich machen können, um …
    Patient:innen müssen den nächsten Termin erkennen können.
    Zweck fehlt
    … um noch diese Woche behandelt zu werden.
    Patient:innen wollen schnell einen Termin.
    Bedürfnis, kein Erfordernis
    In Erfordernisse übersetzen: Was müssen sie dafür erkennen, wissen oder entscheiden können?
    Im System muss die Kassenzulassung angezeigt werden.
    Anforderung ohne Erfordernis und ohne Rolle
    An E „Versicherung vorher wissen“ hängen und so formulieren: Patient:innen müssen im System erkennen können, ob …

    Im Datenmodell

    Erfordernisse hängen am Schritt, Anforderungen am Erfordernis, und erst die Anforderung kennt Screens. Belege verweisen auf die vorhandenen Insights; ohne Beleg legt das Plugin eine Annahme in der Wissensbasis an.

    Die Reifegrad-Leiste unter jedem Schritt wird daraus berechnet: Kontext, Erfordernisse, Anforderungen, Lösung, Evaluation.
